    7. Ausnahmen und Fehler

    Wenn eine Methode einer Klasse auf einen nicht behebbaren Fehler stößt (Datei existiert nicht, Datenbank nicht verbunden, Netzwerkverbindung unterbrochen), gibt sie keinen Fehler auf einer Konsole (Datei, Datenbank) aus, sondern löst eine Ausnahme aus. Ausnahmen erweitern die Klasse [\Exception]. Neben den Ausnahmen löst auch der interne Betrieb von PHP Fehler aus, deren Basisklasse [\Error] ist. Beide Klassen implementieren die Schnittstelle [\Throwable].

    PHP 8 hat die Fehlerbehandlung grundlegend verändert: Viele Situationen, die in PHP 7 nur eine einfache Warnung (und oft ein absurdes Ergebnis) erzeugten, lösen jetzt einen Fehler aus, der abgefangen werden kann. Das werden wir im Verlauf der Beispiele sehen.

    interface Throwable extends Stringable
{
    public function getMessage(): string;
    public function getCode(): int;
    public function getFile(): string;
    public function getLine(): int;
    public function getTrace(): array;
    public function getTraceAsString(): string;

    Die Methoden der Schnittstelle haben folgende Aufgaben:

    Methode
    Zweck
    [getMessage]
    liefert die Fehlermeldung
    [getCode]
    liefert den Fehlercode (eine ganze Zahl)
    [getFile]
    liefert den Namen der Datei, in der das Objekt erzeugt wurde
    [getLine]
    liefert die Zeilennummer, in der das Objekt erzeugt wurde
    [getTrace]
    liefert den Funktionsaufrufstapel als Array
    [getTraceAsString]
    liefert den Aufrufstapel als Zeichenkette
    [getPrevious]
    liefert das vorherige (gekapselte) Objekt [Throwable] oder [null]
    [__toString]
    liefert eine Zeichenkettendarstellung des Objekts

    Beachten Sie, dass die Schnittstelle [Throwable] die im Kapitel über Klassen behandelte Schnittstelle [Stringable] erweitert. Eine Klasse kann die Schnittstelle [Throwable] nicht direkt implementieren; sie muss von [\Exception] oder [\Error] abgeleitet sein.

    7.3. Vordefinierte Ausnahmen und Fehler in PHP 8

    Das folgende Skript [throwables.php] zeigt die Baumstruktur der vordefinierten Klassen an, die die Schnittstelle [Throwable] implementieren. Wir verwenden es, um eine exakte Liste – die von PHP 8.5 – zu erhalten, statt sie aus der Dokumentation abzuschreiben. Sie verpassen nichts, wenn Sie nicht versuchen, den Code zu verstehen, der die Reflection-API von PHP verwendet (die Klasse [ReflectionClass] erlaubt es, PHP nach einer Klasse zu befragen: ihrem Namen, ihrer ursprünglichen Erweiterung, ihren Schnittstellen usw.) und eine rekursive Funktion:

    <?php

// strikte Einhaltung der deklarierten Typen der Funktionsparameter
declare(strict_types=1);

// zeigt den Baum der vordefinierten Klassen an, die die Schnittstelle [Throwable] implementieren
// wir beschränken uns auf die in PHP 8.5 immer vorhandenen Erweiterungen:
// den Kern (Core), die Standardbibliothek, die SPL-Bibliothek, JSON und Random
$extensions = ["Core", "standard", "SPL", "json", "random"];

// die vordefinierten Klassen dieser Erweiterungen, die [Throwable] implementieren
$classes = array_filter(
    get_declared_classes(),
    function (string $class) use ($extensions): bool {
        $reflection = new ReflectionClass($class);
        return $reflection->isInternal()
            && $reflection->implementsInterface(Throwable::class)
            && in_array($reflection->getExtensionName(), $extensions, true);
    }
);
sort($classes);

// rekursive Anzeige der Kindklassen der Klasse [$parent]
function display(?string $parent, array $classes, string $indentation): void
{
    // die direkten Kinder von [$parent]
    $children = array_values(array_filter(
        $classes,
        fn(string $class): bool => (get_parent_class($class) ?: null) === $parent
    ));
    foreach ($children as $i => $child) {
        $last = $i === count($children) - 1;
        print $indentation . ($last ? "└── " : "├── ") . $child . "\n";
        display($child, $classes, $indentation . ($last ? "    " : "│   "));
    }
}

print "Throwable\n";
display(null, $classes, "");

    Kommentare

    • Zeile 13: Die Funktion [get_declared_classes] liefert eine Liste aller an dieser Stelle bekannten Klassen, ob vordefiniert oder nicht;
    • Zeilen 16–18: Es werden nur vordefinierte (interne) Klassen beibehalten – solche, die die Schnittstelle [Throwable] implementieren und zu Erweiterungen gehören, die in PHP 8.5 immer vorhanden sind (Zeile 9). Andere Erweiterungen bringen eigene Ausnahmen mit (zum Beispiel [PDOException] für den Datenbankzugriff, der uns später begegnen wird);
    • Zeilen 24–36: eine rekursive Funktion, die die direkten Kindklassen der Klasse [$parent] anzeigt, dann die Kinder jeder dieser Klassen usw. Die Funktion [get_parent_class] liefert [false] für eine Klasse ohne Elternklasse: Der Operator [?:] wandelt [false] dann in [null] um;
    • Zeile 29: eine Pfeilfunktion (PHP 7.4), eine Kurzform einer anonymen Funktion, die auf einen Ausdruck reduziert ist;
    • Zeile 39: Wir beginnen mit den Klassen ohne Elternklasse: [Error] und [Exception].

    Die Ergebnisse zeigen zwei Familien:

    • die Familie [Exception]: Das sind die Ausnahmen, die von Bibliotheken und Anwendungscode ausgelöst werden. Dazu gehören:
      • [ErrorException], die eine Warnung von PHP in eine Ausnahme umwandelt (wir verwenden sie am Ende des Kapitels);
      • [JsonException] (PHP 7.3), ausgelöst von [json_encode] und [json_decode] mit der Option [JSON_THROW_ON_ERROR];
      • [Random\RandomException] (PHP 8.2), ausgelöst von den Funktionen zur Zufallszahlenerzeugung;
      • die Ausnahmen der SPL-Bibliothek (Standard PHP Library), einer Sammlung von Klassen und Schnittstellen zur Lösung von Problemen, auf die Entwickler häufig stoßen. Sie bilden zwei Unterfamilien:
      • [LogicException] und ihre Ableitungen: Programmierfehler, die sich durch Korrektur des Codes beheben lassen: ungültiges Argument ([InvalidArgumentException]), Wert außerhalb des erwarteten Bereichs ([DomainException]), nicht vorhandene Methode ([BadMethodCallException]) ...;
      • [RuntimeException] und ihre Varianten: Fehler, die sich erst zur Laufzeit erkennen lassen: Index außerhalb der Grenzen ([OutOfBoundsException]), unerwarteter Wert ([UnexpectedValueException]), Kapazität überschritten ([OverflowException]) ...;
    • die Familie [Error]: Das sind Fehler, die von der PHP-Engine selbst ausgelöst werden. Dazu gehören:
      • [TypeError]: Ein Wert hat nicht den erwarteten Typ (Funktionsparameter, typisiertes Attribut, Rückgabewert, Operand eines Operators usw.). Ihre Ableitung [ArgumentCountError] zeigt eine unzureichende Anzahl von Argumenten an;
      • [ValueError] (PHP 8.0): Ein Wert hat den richtigen Typ, aber einen ungültigen Wert (zum Beispiel eine negative Länge oder die Länge null);
      • [ArithmeticError] und ihre Ableitung [DivisionByZeroError]: Fehler bei arithmetischen Operationen;
      • [UnhandledMatchError] (PHP 8.0): Kein Zweig des Ausdrucks [match] passt;
      • [AssertionError]: Die Zusicherung [assert] ist fehlgeschlagen;
      • [CompileError] und ihre Ableitung [ParseError]: Syntaxfehler in einer Datei, die mit [require] oder [include] geladen wird;
      • [FiberError] (PHP 8.1) und [Random\RandomError] (PHP 8.2): Fehler im Zusammenhang mit Fibers und Zufallszahlengeneratoren, die wir nicht verwenden werden.

    Die beiden Familien sind nicht miteinander verwandt: Eine Klausel [catch (\Exception $e)] fängt einen Fehler vom Typ [Error] nicht ab. Nur die Schnittstelle [Throwable] verbindet sie.

    <?php

// strikte Einhaltung der deklarierten Typen der Funktionsparameter
declare(strict_types=1);

// wir zeigen alle Fehler an
error_reporting(E_ALL);
ini_set("display_errors", "1");
// wir umgeben den Code mit einem try / catch
try {
    $var = [];
    // unbekannter Schlüssel
    print $var["abcd"];
    // Division durch null
    $var = 7 / 0;
    var_dump($var);
    // Array mit fester Größe
    $array = new \SplFixedArray(5);
    $array[1] = 2;
    $array[4] = "foo";
    // Index außerhalb der Grenzen
    $array[5] = 8;
    // Prüfung
    print "this message will not be displayed\n";
} catch (\Throwable $ex) {
    // \Throwable ist die Schnittstelle, die von allen Fehlern und Exceptions implementiert wird
    // wir zeigen die Exception an
    print "error, message: " . $ex->getMessage() . ", type: " . $ex::class . "\n";
}

    Kommentare

    • Das Skript ist das im vorigen Abschnitt vorgestellte. Wir haben jedoch den Code, der Fehler verursachen könnte, nun in eine Struktur [try / catch] eingeschlossen: Wenn der Code in den Zeilen 11–24 eine Ausnahme oder einen Fehler auslöst (wirft), wird dieser von der Klausel [catch] in den Zeilen 25–29 behandelt;
    • Zeile 25: Der Parameter der Klausel [catch] ist der Typ der Ausnahme oder des Fehlers, der behandelt werden soll. Indem wir den Typ [\Throwable] angeben, bei dem es sich um eine Schnittstelle handelt, legen wir fest, dass jede Klasseninstanz behandelt werden soll, die die Schnittstelle [\Throwable] implementiert. Da alle Fehler- und Ausnahmeklassen diese Schnittstelle implementieren, behandelt die Klausel [catch] hier alle Fehler und Ausnahmen;
    • Zeile 15: die Anweisung, die den Fehler auslöst. Sobald eine Ausnahme auftritt, geht die Steuerung an die Klausel [catch] über. Der in [try] folgende Code wird daher nicht ausgeführt;
    • Zeile 28: Die Notation [$ex::class] liefert den Klassennamen des Objekts [$ex].

Die Ausführung zeigt, dass dieser Fehler eine Ausnahme vom Typ [OutOfBoundsException] auslöst (Zeile 2 der Ergebnisse). Im PHP-7-Kurs (und noch in PHP 8.3) war es eine Ausnahme vom Typ [RuntimeException]. Die Änderung hat bestehenden Code nicht beeinträchtigt, da die Klasse [OutOfBoundsException] von der Klasse [RuntimeException] abgeleitet ist;
      • Zeile 15: behandelt einen Fehler vom Typ [\Throwable]. Das ist zulässig, da der Typ [OutOfBoundsException] vom Typ [\Exception] abgeleitet ist, der die Schnittstelle [\Throwable] implementiert;
      • Zeile 23: behandelt einen Fehler vom Typ [\Exception]. Das ist zulässig, da der Typ [OutOfBoundsException] vom Typ [\Exception] abgeleitet ist;
      • Zeile 31: behandelt einen Fehler vom Typ [\RuntimeException]. Das ist zulässig, da der Typ [OutOfBoundsException] vom Typ [\RuntimeException] abgeleitet ist. Das ist eine gute Wahl: Der Code funktioniert unabhängig von der PHP-Version;
      • Zeile 39: behandelt den genauen Typ der erzeugten Ausnahme;

      • Zeile 47: Jeder Fehler, der die Schnittstelle [\Throwable] implementiert, wird abgefangen. Das ist zulässig;
      • Zeile 55: Der genaue Typ des Fehlers wird abgefangen; dies ist die bevorzugte Methode;

    7.7. Die Klausel [finally]

    Die Struktur [try / catch] kann ein drittes Element haben und so zu einer Struktur [try / catch / finally] werden. Der Code der Klausel [finally] wird in den folgenden beiden Fällen ausgeführt:

    • Die Klausel [try] löst keine Ausnahme aus. Sie wird dann vollständig ausgeführt, danach geht die Ausführung zur Klausel [finally] über, die ebenfalls vollständig ausgeführt wird;
    • Die Klausel [try] löst eine Ausnahme aus. Sie wird dann bis zur Anweisung ausgeführt, die die Ausnahme auslöst. Danach geht die Ausführung zur Klausel [catch] über, die vollständig ausgeführt wird. Anschließend geht die Ausführung zur Klausel [finally] über, die vollständig ausgeführt wird.

    Schließlich wird der Code der Klausel [finally] trotzdem ausgeführt. Dieses Szenario ist im folgenden Fall nützlich:

    • In der Klausel [try] hat der Code Ressourcen belegt (Dateien, Datenbanken, Netzwerkverbindungen, Warteschlangen). Diese Ressourcen sind in der Regel teuer. Sie müssen daher so schnell wie möglich freigegeben (meist „geschlossen“ genannt) werden;
    • Wurden die Ressourcen in [try] belegt, übernimmt [finally] ihre Freigabe. So ist sichergestellt, dass die belegten Ressourcen in jedem Fall (ob ein Fehler auftritt oder nicht) an das System zurückgegeben werden.

    • Zeile 22: Die Division durch null löst einen Fehler [DivisionByZeroError] aus (Zeile 5). Das war bereits in PHP 7 so: Nur die Division durch null mit [/] erzeugte dort eine einfache Warnung;
    • Zeile 28: Eine arithmetische Operation mit einem Array verursacht einen Fehler [TypeError] (Zeile 6);
    • Zeile 34: In PHP 7 löste eine arithmetische Operation mit einer nicht numerischen Zeichenkette die Warnung „A non-numeric value encountered“ aus, und die Zeichenkette wurde als 0 behandelt. In PHP 8 ist das ein Fehler [TypeError] (Zeile 7). Eine numerische Zeichenkette (["12" * 2]) wird weiterhin akzeptiert;
    • Zeile 40: In PHP 7 löste die Übergabe eines Parameters des falschen Typs an eine vordefinierte Funktion eine Warnung aus, und die Funktion lieferte [null]. In PHP 8 lösen alle vordefinierten Funktionen einen Fehler [TypeError] aus, genau wie die vom Entwickler geschriebenen Funktionen (Zeile 8). Die Meldung bezeichnet den Parameter durch seine Nummer und seinen Namen;
    • Zeile 46: Der Parameter hat den richtigen Typ ([int]), aber einen ungültigen Wert (eine Länge muss positiv sein): Das ist der Fehler [ValueError], neu in PHP 8.0 (Zeile 9). In PHP 7 war das eine Warnung;
    • Zeile 52: Die Funktion [sum] erwartet zwei Argumente, erhält aber nur eines: Fehler [ArgumentCountError] (Zeile 10);
    • Zeilen 59–62: Der Ausdruck [match] hat keinen Zweig für den Wert 8 und keinen Zweig [default]: Fehler [UnhandledMatchError] (Zeile 11). Das ist ein wesentlicher Unterschied zur Anweisung [switch], die nichts tut, wenn kein [case] passt;
    • Zeile 69: Der Aufruf einer Methode auf [null] führt zu einem Fehler [Error] (Zeile 12). Das war bereits in PHP 7 so;
    • Zeile 74: Der Null-Safe-Operator [?->] (PHP 8.0) liefert [null] , wenn das Objekt [null] ist, anstatt die Methode aufzurufen. So muss kein Test [if ($object !== null)] geschrieben werden (Zeile 13).

    Diese Änderungen machen PHP-8-Programme sicherer: Ein Fehler stoppt die Verarbeitung, anstatt sie mit falschen Daten fortzusetzen. Sie verlangen vom Entwickler aber auch, die entsprechenden Klauseln [catch] einzubauen.

    <?php

// strikte Einhaltung der deklarierten Typen der Funktionsparameter
declare(strict_types=1);

// [throw] ist seit PHP 8.0 ein Ausdruck: er kann nach ?? oder in einer Pfeilfunktion verwendet werden
function readAge(array $data): int
{
    $age = $data["age"] ?? throw new \InvalidArgumentException("The age is missing");
    return is_int($age) && $age >= 0 ? $age : throw new \DomainException("Invalid age [$age]");
}

// eine Pfeilfunktion, die nur eine Exception wirft
$forbidden = fn(string $operation) => throw new \LogicException("Operation [$operation] forbidden");

// Testdaten
$tests = [["age" => 48], [], ["age" => -4]];
foreach ($tests as $i => $data) {
    try {
        print "test $i: age=" . readAge($data) . "\n";
    } catch (\InvalidArgumentException | \DomainException $ex) {
        // eine einzige [catch]-Klausel für zwei Exception-Typen
        print "test $i: " . $ex::class . ": " . $ex->getMessage() . "\n";
    }
}

try {
    $forbidden("deletion");
} catch (\LogicException) {
    // seit PHP 8.0 ist die Variable der [catch]-Klausel optional
    print "the operation was refused\n";
}

// Einhüllen einer Low-Level-Exception in eine Anwendungs-Exception
class DaoException extends \RuntimeException
{
}

function readConfiguration(string $json): array
{
    try {
        return json_decode($json, true, flags: JSON_THROW_ON_ERROR);
    } catch (\JsonException $ex) {
        // die ursprüngliche Ursache wird als 3. Parameter übergeben: sie geht nicht verloren
        throw new DaoException("Unreadable configuration", 10, $ex);
    }
}

try {
    readConfiguration('{"dsn": "mysql:host=localhost"');
} catch (DaoException $ex) {
    print $ex::class . ": " . $ex->getMessage() . " (code " . $ex->getCode() . ")\n";
    print "cause: " . $ex->getPrevious()::class . ": " . $ex->getPrevious()->getMessage() . "\n";
}

    • Zeile 9: Ab PHP 8.0 ist [throw] ein Ausdruck und nicht mehr nur eine Anweisung. Es kann daher überall dort verwendet werden, wo ein Wert erwartet wird: hier nach dem Operator [??]. Existiert der Schlüssel [age] nicht, wird eine Ausnahme ausgelöst; andernfalls wird [$age] sein Wert zugewiesen;
    • Zeile 10: [throw] in einem bedingten Ausdruck [? :] verwendet;
    • Zeile 14: eine Pfeilfunktion, deren Rumpf lediglich eine Ausnahme auslöst. Vor PHP 8.0 war das nicht möglich: Eine Pfeilfunktion darf nur einen Ausdruck enthalten;
    • Zeile 21: eine einzige Klausel [catch] für zwei Ausnahmetypen (Zeilen 3–4 der Ergebnisse). Beachten Sie, dass [InvalidArgumentException] und [DomainException] beide von [LogicException] abgeleitet sind: Ein [catch (\LogicException $ex)] hätte dieselbe Wirkung gehabt;
    • Zeile 29: Ab PHP 8.0 ist die Variable in der Klausel [catch] optional, wenn man nicht die Ausnahme selbst, sondern nur ihren Typ benötigt (Zeile 5);
    • Zeilen 35–37: eine anwendungsspezifische Ausnahme. In den folgenden Kapiteln schreiben wir Datenzugriffsschichten (DAO, Data Access Object), die nur diesen Ausnahmetyp auslösen, unabhängig von der Fehlerquelle (Datei, JSON, Datenbank);
    • Zeilen 39–47: Die Funktion [readConfiguration] dekodiert eine JSON-Zeichenkette. Die Low-Level-Ausnahme [JsonException] wird abgefangen und (Zeile 45) in eine Ausnahme [DaoException] verpackt. Die ursprüngliche Ursache wird als dritter Parameter an den Konstruktor übergeben;
    • Zeile 53: Der aufrufende Code kennt nur [DaoException], kann aber die ursprüngliche Fehlerursache mit der Methode [getPrevious] abrufen (Zeilen 6–7 der Ergebnisse).

    7.13. Warnungen in Ausnahmen umwandeln: [ErrorException]

    Trotz der Verbesserungen in PHP 8 bleiben bestimmte Anomalien bloße Warnungen: nicht vorhandener Array-Schlüssel, nicht definierte Variable, Datei, die sich mit [fopen] nicht öffnen lässt ... Diese Warnungen lassen sich nicht mit einem [try / catch] abfangen. Sie können jedoch einen Fehlerhandler installieren, der sie in Ausnahmen vom Typ [ErrorException] umwandelt. Genau das tut das Skript [exceptions-11.php]:

// strikte Einhaltung der deklarierten Typen der Funktionsparameter
declare(strict_types=1);

// Fehlerbehandler: wandelt PHP-Warnungen in [ErrorException]-Exceptions um
set_error_handler(function (int $level, string $message, string $file, int $line): bool {
    throw new \ErrorException($message, 0, $level, $file, $line);
});

// ein unbekannter Schlüssel löst nicht mehr nur eine Warnung, sondern eine Exception aus
$person = ["lastName" => "Langevin"];
try {
    print $person["firstName"] . "\n";
} catch (\ErrorException $ex) {
    print "Error: " . $ex->getMessage() . " (line " . $ex->getLine() . ")\n";
    print "level E_WARNING: " . var_export($ex->getSeverity() === E_WARNING, true) . "\n";
}
// dasselbe beim Öffnen einer nicht existierenden Datei
try {
    $stream = fopen(__DIR__ . "/nonexistent.txt", "r");
} catch (\ErrorException $ex) {
    print "Error: " . $ex->getMessage() . "\n";
}
// wir kehren zum PHP-Fehlerbehandler zurück
restore_error_handler();
print "end\n";

    Kommentare

    • Zeilen 7–9: Die Funktion [set_error_handler] richtet einen Fehlerhandler ein – eine Funktion, die PHP aufruft, sobald eine Warnung, ein Hinweis oder eine Deprecation-Meldung auftritt, anstatt die Meldung anzuzeigen. Sie erhält die Fehlerstufe, die Fehlermeldung, die Datei und die Zeile, in der der Fehler aufgetreten ist. Hier löst sie eine Ausnahme vom Typ [ErrorException] aus, die diese Informationen speichert. Der Rückgabetyp [bool] entspricht der Angabe in der Dokumentation von [set_error_handler]: Die Funktion würde [false] zurückgeben, damit PHP den Fehler normal behandelt. Hier gibt sie nie etwas zurück, weil sie immer eine Ausnahme auslöst;
    • Zeile 14: Der Schlüssel [firstName] existiert nicht. Anstelle einer Warnung wird eine Ausnahme [ErrorException] ausgelöst und abgefangen (Zeile 2 der Ergebnisse);
    • Zeile 17: Die Methode [getSeverity], die für die Klasse [ErrorException] spezifisch ist, liefert die Stufe des ursprünglichen Fehlers (Zeile 3);
    • Zeile 21: Auch der Versuch, eine nicht vorhandene Datei zu öffnen, führt zu einer Ausnahme (Zeile 4);
    • Zeile 26: stellt den vorherigen Fehlerhandler wieder her, in diesem Fall den von PHP.

    Diese Technik wird von vielen PHP-Frameworks (Symfony, Laravel) verwendet: Während der Entwicklung wird jede Warnung zu einer Ausnahme, was den Entwickler zwingt, den Code zu korrigieren. Das Testwerkzeug [PHPUnit], das wir später verwenden werden, funktioniert ähnlich: Es kann einen Test fehlschlagen lassen, wenn dieser eine Warnung oder eine Deprecation-Meldung erzeugt.
